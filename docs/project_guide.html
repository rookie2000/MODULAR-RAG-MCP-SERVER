Modular RAG MCP Server

一个基于 Model Context Protocol 的模块化检索增强生成框架 — 从零开始的学习指南

RAG MCP Protocol Hybrid Search Vector DB Python 3.10

项目概述

这个项目做了一件事：让你的 AI 助手（如 Claude Desktop）能搜索你自己的私有文档。 你把 PDF 扔进去，它帮你切成块、向量化、建索引，然后通过标准协议（MCP）对外提供问答服务。

通俗比喻：一家智能图书馆

把整个项目想象成一家图书馆

Ingestion（摄入层）

图书管理员把新书拆开、贴标签、编目录、上架。对应：PDF → 切块 → 向量化 → 存储

Query Engine（检索引擎）

读者来问问题，管理员用"关键词搜索 + 分类索引"两种方式帮你找书。对应：混合检索 + RRF融合

Response（响应层）

管理员把找到的内容整理成一段带出处的回答。对应：Markdown + 引用标记 + 图片

MCP Server（服务窗口）

图书馆的对外窗口，外部的人通过这个窗口来提问。对应：JSON-RPC over stdio

👁️ Observability（监控室）

图书馆的监控室，记录每一次借阅和每一次采购的详细日志。对应：TraceContext + Streamlit Dashboard

五大架构层详解

每一层都有明确的职责，层与层之间通过数据类型（Document、Chunk、RetrievalResult）解耦，可以独立替换和测试。

1️⃣ MCP Server — 对外的"门面"

它是整个系统的入口，通过 MCP 协议对外暴露 3 个工具：

工具名功能参数
query_knowledge_hub核心：接收问题，返回带引用的答案query (必填), top_k, collection
list_collections列出有哪些文档集合无
get_document_summary返回某份文档的摘要collection, document_id
工作方式：通过 stdio（标准输入输出）传输 JSON-RPC 消息。 客户端发一个 tools/call("query_knowledge_hub", {"query": "xxx"})， server 端就会调起下面所有层来完成一次查询。

关键文件

  • src/mcp_server/server.py — 入口，创建 MCP Server 实例
  • src/mcp_server/protocol_handler.py — 工具注册表，管理 3 个工具的 schema 和执行
  • src/mcp_server/tools/query_knowledge_hub.py — 核心查询工具，编排整个查询流程

2️⃣ Ingestion — 文档"吃进去"的流水线

把 PDF 文档处理成可检索的数据，存进向量库。一条文档经过 6 个阶段：

阶段 1
完整性检查 — SQLiteIntegrityChecker
计算文件的 SHA256 哈希值，查 SQLite 数据库。如果文件已经处理过且没变化，直接跳过，省时间省 API 调用。
阶段 2
文档加载 — PdfLoader
用 markitdown 把 PDF 转成 Markdown 文本，同时提取图片。输出一个 Document 对象。
阶段 3
分块 — DocumentChunker
按配置的 chunk_size（默认 1000 字符）把文档切成小块，块之间有 200 字符重叠，防止关键信息被切断。输出 List[Chunk]。
阶段 4
转换 — ChunkRefiner + MetadataEnricher + ImageCaptioner
清洗块边界文本、用 LLM 补充标题/标签/摘要等元数据、用视觉模型给图片加文字描述。
阶段 5
编码 — DenseEncoder + SparseEncoder
调用 Embedding API 生成向量（Dense），同时统计词频生成 BM25 索引数据（Sparse）。两条路并行产出。
阶段 6
存储 — VectorUpserter + BM25Indexer + ImageStorage
向量写入 ChromaDB，BM25 索引落盘，图片注册到 SQLite。最后在 ingestion_history 里标记完成。

关键数据类型流转

Document  →  Chunk  →  ChunkRecord
  (原始文档)     (分块后)      (分块 + 向量)

3️⃣ Query Engine — 检索"找东西"的核心

为什么要混合检索？

Dense（向量搜索）

把问题向量化 → 在 ChromaDB 里做余弦相似度搜索。
优势：理解语义，"猫"和"猫咪"能匹配上。
劣势：可能忽略精确关键词。

Sparse（BM25 关键词搜索）

用关键词在 BM25 索引里打分。
优势：精确匹配关键词很准。
劣势：不懂语义，"猫"和"猫咪"对它来说是不同的词。

RRF 融合为什么不用原始分数？
因为两条路线的分数不可比——向量搜索的分数是 0~1（余弦相似度），BM25 的分数可以是任意正数。 RRF 只看"你在这条路线里排第几名"，用 1/(60+rank) 公式来统一，简单有效。
⚠️ 优雅降级：如果 Dense 挂了就用 Sparse-only，反之亦然。两个都挂才报错。

4️⃣ Response — 组装"漂亮答案"的层

把检索到的原始结果，整理成人可读的 Markdown 答案。

CitationGenerator

给每个结果生成 [1] [2] 引用标记，提取来源路径、页码、相关度百分比。

️ MultimodalAssembler

如果结果涉及图片，加载文件 → 检测 MIME 类型 → base64 编码 → 和文本一起返回。

ResponseBuilder

把上面的内容拼成结构化 Markdown，同时输出 JSON 供程序解析。

输出格式示例

## 检索结果

### 结果 1 [1]
- 来源: 技术文档.pdf
- 页码: 3
- 相关度: 92.5%

> 检索到的文本内容...

## 引用来源
[1] 技术文档.pdf (第3页)

5️⃣ Observability — "监控仪表盘"

记录和可视化每一次查询/摄入的详细过程。

运行步骤（从零开始）

以下每一步都说明了做什么和为什么要这样做。

0安装工具：uv 包管理器

# Windows PowerShell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh
为什么要这样做？
这个项目依赖十几个外部库（chromadb 做向量存储、jieba 做中文分词、mcp 做协议通信等）。 你需要一个包管理器来统一下载和管理它们，确保版本对得上。
为什么用 uv 而不是 pip？strong> uv 比 pip 快 10-100 倍，能自动管理虚拟环境，锁定依赖版本，避免"在我机器上能跑"的问题。

1创建虚拟环境 + 安装依赖

cd D:\MODULAR-RAG-MCP-SERVER
uv sync --extra dev
这一行做了什么？
① 在项目目录下创建一个 .venv/ 文件夹（虚拟环境）
② 根据 pyproject.toml 里的依赖清单，把所有需要的库装进去

为什么要虚拟环境？
如果直接装到系统 Python 里，不同项目的依赖版本会冲突（A 项目要 numpy 1.x，B 项目要 numpy 2.x）。 虚拟环境相当于给每个项目一个独立的"小房间"，互不干扰。

2配置 API 密钥

# 复制模板文件
cp config/test_credentials.yaml.example config/test_credentials.yaml

然后编辑 config/test_credentials.yaml，填入你的 API Key：

mimo:
  api_key: "你的密钥"        # 默认的 LLM（大语言模型）提供商
  model: "mimo-v2-pro"
  base_url: "https://token-plan-cn.xiaomimimo.com/v1"

minimax:
  api_key: "你的密钥"        # 默认的 Embedding（向量化）提供商
  embedding_model: "embo-01"
  base_url: "https://api.minimax.chat/v1"
为什么需要 API Key？
这个项目做两件需要 AI 能力的事：
LLM（大语言模型）：用来回答问题、给图片加描述、补充元数据。
Embedding（向量化）：把文本变成数学向量（1536 个数字的数组），这样计算机才能比较"两段话有多相似"。

这些都是调用外部 AI 服务，所以需要密钥认证。
为什么分两个提供商？ 做文本理解和做向量化是两种不同的 AI 能力，没必要用同一家。

3检查配置文件

打开 config/settings.yaml，确认关键配置：

配置项默认值含义
llm.provider"openai"用哪家 LLM（openai 兼容接口）
llm.model"mimo-v2-pro"用哪个模型
embedding.provider"minimax"用哪家向量化服务
embedding.dimensions1536向量是 1536 维的
vector_store.provider"chroma"用 ChromaDB 存向量
ingestion.chunk_size1000每 1000 个字符切一刀
ingestion.chunk_overlap200相邻块之间重叠 200 字符
rerank.enabledfalse重排序默认关了（省 API 调用）
为什么需要配置文件？
因为这个项目是"可插拔"的——你可以换 LLM 提供商、换向量库、换切块大小，不用改代码，只改配置就行。

chunk_size 和 chunk_overlap 是什么？
把文档切成小块才能精确检索。如果一块太大（比如一整章），搜索时会包含很多无关内容；太小又丢失上下文。 重叠 200 字符是为了防止在块的边界处把一句话切断。

4验证环境能跑

uv run python main.py
为什么要先验证？
就像做菜前先检查有没有食材。如果这里报错（比如 API Key 没填、依赖没装好），后面所有步骤都会失败。 看到 "Settings loaded successfully" 就说明环境和配置都没问题。

5把文档"喂"给系统

# 先用 --dry-run 试一下，只解析不真正入库
uv run python scripts/ingest.py --path tests/fixtures/sample_documents --dry-run

# 没问题后，真正执行入库
uv run python scripts/ingest.py --path tests/fixtures/sample_documents --collection demo
这一步发生了什么？
PDF → SHA256 去重 → 提取文本和图片 → 切成小块 → 清洗+补充元数据 → 调 Embedding API 生成向量 → 向量存入 ChromaDB + BM25 索引落盘

为什么要先 dry-run？
就像先排练再正式演出。dry-run 只跑解析流程，不真正调 API 和写数据库，可以提前发现格式问题，省钱省时间。

为什么必须做这一步？
就像图书馆必须先采购、编目、上架，读者才能查到书。系统必须先把文档处理成向量存好，后面才能检索。

6查询知识库

uv run python scripts/query.py --query "什么是混合检索？" --verbose
这一步发生了什么？
你的问题 → jieba 分词提取关键词 → 同时跑 Dense（向量搜索）和 Sparse（BM25 关键词搜索）两条路线 → RRF 融合两路排名 → 返回 top-k 个最相关的文档块。

为什么要搞两条路线？
Dense 理解语义但可能忽略精确关键词；Sparse 精确匹配但不懂语义。两条路一起跑，取长补短，召回率更高。

7启动 Dashboard 可视化

uv run python scripts/start_dashboard.py --port 8501

浏览器打开 http://localhost:8501。

为什么要这个？
就像开车需要仪表盘。当你发现搜索结果不好时，Dashboard 能帮你定位问题—— 是 Dense 没搜到东西？还是融合后排错了？还是 Rerank 把好的结果踢掉了？ 它会用柱状图展示每个阶段的耗时，用表格展示每个阶段的中间结果。

8把 MCP Server 接入 AI 助手

# 启动 MCP Server
uv run python -m src.mcp_server.server

在 Claude Desktop 配置文件中添加：

{
  "mcpServers": {
    "modular-rag": {
      "command": "uv",
      "args": ["run", "python", "-m", "src.mcp_server.server"],
      "cwd": "D:\\MODULAR-RAG-MCP-SERVER"
    }
  }
}
为什么需要 MCP？
MCP 是一个标准协议，让 AI 助手知道"这里有一个工具可以用"。配好之后，你在 Claude Desktop 里问问题， Claude 会自动调用 query_knowledge_hub 来搜你的知识库，然后把结果整合进它的回答。

为什么用 stdio？
MCP Server 通过标准输入输出和客户端通信，不走网络端口。更安全——不需要开端口，不需要处理网络问题，进程间直接对话。

一句话总结

先"喂书"（Ingestion），再"查书"（Query Engine），通过"服务窗口"（MCP Server）对外提供服务，用"监控室"（Observability）随时检查系统状态。 各层之间通过 Document、Chunk、RetrievalResult 等数据类型解耦，每层可以独立替换和测试。
